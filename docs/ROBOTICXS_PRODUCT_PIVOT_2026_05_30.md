# Roboticxs Product Pivot 2026-05-30

## 1. Pivot thesis

Roboticxs should stop proving only that it can safely avoid doing things, and start proving that it can safely help with things people actually pay to stop doing themselves.

The current runtime has strong internal governance, but the product narrative is still too close to retrieval governance and not close enough to user pain relief.

## 2. Comparison with the current brief

The original brief correctly positioned Roboticxs as:
- the personal robot layer in the Roboticxs -> Agentius -> Zaubern chain
- a product with memory, skills, routing, and action boundaries
- a B2C / prosumer / small business entry point

What changes now is not the underlying architecture.

What changes is the center of gravity:
- from personal AI robot for productivity theater
- to personal admin robot for recurring life/work headaches

## 3. Target-user correction

The main customer should not be framed as a power user trying to control AI.

The main customer should be someone who:
- forgets things
- has recurring admin burden
- feels anxiety from pending actions
- may be intimidated by technology
- would gladly pay for reliable preparation, reminders, and bounded help

Power users remain useful as signal, not as the primary audience.

## 4. New product center of gravity

Roboticxs is a personal robot for:
- pendientes
- memoria
- skills
- approvals
- bounded action

User-facing framing:
- Robbie prepares
- Robbie organizes
- Robbie reminds
- Robbie asks before acting

Plain-language promise:
- Robbie prepares. You decide.
- Nothing important happens without your permission.

## 5. Core workflow: Que se me paso

The strongest near-term workflow is:
- Que se me paso
- What did I miss
- Que necesita mi atencion

Why this matters:
- it is broad
- it is understandable
- it is useful before live connectors
- it turns current internal state into visible value

It can use existing local state:
- active memories
- document reviews
- file metadata
- retrieval intents
- budget posture
- tasks/task_runs
- pending approvals and control states

## 6. Robot Folder / Mi informacion importante

Roboticxs needs a human-facing structure for important recurring context.

Recommended sections:
- Sobre mi
- Casa
- Auto
- Familia
- Papas / suegros
- Servicios
- Contactos importantes
- Preferencias
- Cosas que Robbie nunca debe hacer

This should be exposed as simple personal structure, not as technical source-of-truth jargon.

## 7. Skill Catalog + Capability Resolver

Skills should be organized around pains, not generic productivity categories.

One recurring headache can become one skill.

Robbie should be able to answer:
- Eso ya lo puedo hacer
- Eso existe pero hay que activarlo
- Eso requiere configuracion
- Eso todavia no existe, pero puedo registrarlo
- Eso no puedo hacerlo de forma segura

This turns Robbie into a natural lead generator for Agentius.

## 8. Super Familiar / caregiver wedge

The best concrete wedge is caregiver admin, starting with:
- Super Familiar

This is not just grocery convenience.
It is recurring caregiver burden with clear emotional and practical value.

Initial bounded behavior:
- habitual list
- preferred brands
- substitutions
- budget
- delivery window
- user approval before payment

Boundary:
- Robbie prepares
- user approves
- no silent payment

## 9. Web Workflow Preflight

Many valuable Roboticxs workflows are web-admin tasks, not retrieval tasks.

Examples:
- Telmex payment preparation
- vehicle verification preparation
- grocery cart preparation
- reservations
- appointment preparation

Execution principle:
- server-side robot prepares
- user reviews and approves
- no irreversible action happens silently

## 10. Robbie as lead generator for Agentius

Every user request can map to one of these states:
- active for user
- available to activate
- available but needs setup
- new vertical candidate
- prohibited or restricted

That lets Robbie surface demand safely:
- what already exists
- what needs configuration
- what should become a future Agentius workflow

## 11. Zaubern as internal trust layer

Zaubern remains important, but as internal control/authority infrastructure.

It should not become the consumer-facing headline.

Its value inside Roboticxs is:
- no silent authority expansion
- no silent external execution
- no silent payments
- no silent memory
- no false claims from metadata-only flows

## 12. Pricing pivot

Pricing should reflect pain relief, not code complexity.

Recommended direction:
- base subscription
- usage-sensitive economics
- one-time skill activation or setup where appropriate

That is a better fit than turning every skill into an abstract monthly add-on.

## 13. What remains true

These original principles still stand:
- one robot, many skills
- memory approval
- local boundaries
- routing visibility
- budget as authority surface
- Agentius upgrade path
- Zaubern as deeper authority layer

The pivot changes product emphasis and roadmap priority, not the architectural foundation.

## 14. Product roadmap pivot

The retrieval-control ladder is sufficient for now and should be frozen unless a future approved stage reopens it.

The next product stages should focus on utility:
- Stage 26P — Product Reorientation / Runtime Status Alignment
- Stage 27P — Que se me paso v0
- Stage 28P — Robot Folder / Mi informacion importante
- Stage 29P — Skill Catalog + Capability Resolver
- Stage 30P — Super Familiar v0
- Stage 31P — Web Workflow Preflight Framework
- Stage 32P — Skill Activation + Pricing Metadata
- Stage 33P — Opportunity Log / Agentius Lead Handoff
